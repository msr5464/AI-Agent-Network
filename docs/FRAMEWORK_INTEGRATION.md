# Framework Integration Guide

QA Agent Network uses a **Framework Plugin Suite** architecture to remain framework-agnostic. The core AI agents handle the orchestration, reasoning, and prompt generation, while **Framework Plugins** handle the underlying syntax, execution, and artifact parsing.

This guide explains how to build a new Framework Plugin (e.g., for Cypress, WebDriverIO, or Appium) and what the target automation repository MUST provide for the agents to operate with high confidence.

## Step 1: Create the Python Plugin

To integrate a new framework, you must create a new plugin in `shared/frameworks/<name>_plugin.py` that implements the five core interfaces defined in `shared/frameworks/base.py`.

### 1. `TelemetryParser`
**Purpose:** Reads the execution artifacts generated by a failed test to reconstruct the timeline of events.
**Requirements:**
- `read_actions`: Must return a list of dictionaries representing every action taken before failure.
- `failing_action`: Must return the specific action that threw the exception.
**Why it matters:** The AI needs to see *what worked* before the test failed to understand the context.

### 2. `TestRunner`
**Purpose:** Determines how to execute a specific test class/method from the command line.
**Requirements:**
- `detect_command`: Inspects the `workspace` path and returns the CLI arguments (e.g., `["npx", "cypress", "run", "--spec", "..."]`).
- `apply_browser_mode`: Ensures that global variables like `HEADLESS_BROWSER=true` are translated into the framework's native CLI flags.

### 3. `DiagnosticEngine`
**Purpose:** Translates framework-specific error messages into semantic categories.
**Requirements:**
- `is_ambiguous_locator`: Returns `True` if the error trace explicitly indicates that multiple elements matched the selector. (If your framework silently picks the first match and doesn't throw, return `False`).

### 4. `CodeEngine`
**Purpose:** The hardest part. This acts as the AST parser and code generator for the framework.
**Requirements:**
- `extract_locators`: Given the source code of a Page Object file, it must use regex/AST to find every declared locator (e.g., `@FindBy`, `page.locator()`, `cy.get()`).
- `normalize_selector`: Converts native locators into pure CSS so the AI can evaluate them against the captured DOM. (Return `None` for XPath).
- `emit_locator`: Takes generic attributes (`role`, `text`, `testid`) and emits the native Python and Java code to click it.

### 5. `MCPProvider`
**Purpose:** Configures the LLM's connection to the live browser for exploration.
**Requirements:**
- Return the JSON configuration for the MCP server.
- **Note:** Because the DOM is universal, you can often reuse the `@playwright/mcp` server here just for DOM inspection, even if your execution framework is Selenium or Cypress!

## Step 2: Update the Factory

Once your plugin is written, register it in `shared/frameworks/__init__.py`:

```python
def get_active_plugin() -> FrameworkPlugin:
    framework = os.environ.get("AUTOMATION_FRAMEWORK", "playwright").lower()
    if framework == "cypress":
        from shared.frameworks.cypress_plugin import CypressPlugin
        return CypressPlugin()
```

## Step 3: Target Repository Requirements (The "Must-Haves")

For the QA Agent Network to fix broken tests successfully, the target automation repository being tested **MUST** provide three specific artifacts whenever a test fails. 

If the target framework does not provide these natively, **you must write a custom listener/reporter in the target repository to generate them.**

### 1. The DOM Snapshot (MANDATORY)
**What:** The complete HTML of the page at the exact moment the test crashed.
**Why:** The AI uses this to find the replacement locator. Without it, the AI is completely blind and will hallucinate.
**How:** Your target repo must dump `document.documentElement.outerHTML` to a file upon failure.

### 2. The Action Timeline / Telemetry (MANDATORY)
**What:** A structured log of every click, type, and navigation action that occurred during the test, including the locator used and the time it took.
**Why:** The AI uses this to understand the sequence of events leading to the failure.
**How:** If your framework doesn't have native tracing (like Playwright does), you must implement an Event Listener in your target repo that appends JSON lines to a `telemetry.jsonl` file before and after every action.

### 3. Parked Repair Mode / CDP Port (OPTIONAL BUT HIGHLY RECOMMENDED)
**What:** When a test fails in "repair mode", the framework leaves the browser open and dumps the Chrome DevTools Protocol (CDP) port (e.g., `http://localhost:9222`) into the failure log.
**Why:** This allows the AI to attach to the exact crashed state and use the MCP server to inspect the live page interactively.
**How:** Launch Chrome with `--remote-debugging-port=9222` and write that port to the test output JSON.

## Step 4: Quality Benchmarking

Before deploying your new plugin to production, you MUST benchmark it against the `locator-eval` suite.

1. Ensure `AUTOMATION_FRAMEWORK=<your_framework>` is set.
2. Run the locator evaluation baseline:
   ```bash
   pytest locator-eval/
   ```
3. Your plugin must extract locators and generate valid code syntax with the same success rate as the reference `PlaywrightPlugin`.
